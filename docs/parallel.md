# syndrilla-parallel: shot-parallel multi-GPU decoding

This note explains the design of the `syndrilla-parallel` launcher: what it does that the problem alone does not dictate, why, and what it buys. The flag table and the user-facing contract live in the README under [Run with command line arguments](../README.md#1-run-with-command-line-arguments) (the `syndrilla-parallel` paragraph and its table) and [Sweep configurations](../README.md#5-sweep-configurations). This note does not repeat them.

Source files: `src/syndrilla/parallel.py` (the `run` launcher), `src/syndrilla/sweep.py` (`sweep-gen` and `sweep`), `src/syndrilla/main.py` (the worker), `src/syndrilla/metric/metric.py` (result YAML and checkpoint), `src/syndrilla/utils/utils.py` (the deferred queue). Line numbers refer to the current working tree. The command is installed from `pyproject.toml:39-41` (`syndrilla-parallel = "syndrilla.parallel:main"`); the launcher spawns workers as `python -m syndrilla.main` with its own interpreter (`parallel.py:560`), not through the `syndrilla` console script.

`tests/test_parallel.py` and `tests/test_sweep.py` cover the launcher's planning, refusals and the sweep slot pick; `resume_seed`, `wilson` and `pooled_now` have no test of their own.

## 1. Shot-parallel worker processes, one flat list with a device each

**Problem.** A Monte Carlo decoding run draws independent shots until a target count of logical errors or batches is reached. The run has to use several GPUs, survive a kill, resume, and give one pooled result.

**Importance.** The alternative is one process that spans GPUs (data parallel or `torch.distributed`). That design couples the GPUs. One out-of-memory or one hang stops all. A resume needs a global checkpoint. Every decoder, kernel and extension load would have to be multi-device aware. Getting this wrong means lost shots or a launcher that cannot restart.

**Innovation.** The launcher runs ordinary single-GPU `syndrilla` processes (workers), one or more per GPU, each in its own directory, each with its own result YAML and checkpoint. The launcher itself never touches a decoder: it plans, probes, spawns, polls the YAMLs, stops, and merges. Shots are the unit of parallelism, so workers share nothing. Workers are a flat list `w0, w1, ...`, each with its own device string; the GPU is a property of the worker, not a level of the layout, so the same plan, resume and merge code serves one GPU, many GPUs, a CPU run, and a sweep point that shares a GPU with another. The code states no rationale for processes over an in-process design; the properties below are what the code gives, not a quoted justification.

**Implementation.**
- `plan_workers` (`parallel.py:527-576`) builds the device list GPU-major, `devices = [device for device in ids for _ in range(args.workers_per_gpu)]` (`parallel.py:539`), and one plan entry per index `i`: the name `w<i>` (`parallel.py:540`), the directory `<run_dir>/w<i>/` (`parallel.py:550`), its target share, seed, resume checkpoint, command and environment. With `--gpus 0 1 --workers-per-gpu 2`, w0 and w1 run on GPU 0 and w2 and w3 on GPU 1. `plan_workers` also takes an explicit `devices` list (`parallel.py:527`), which is how a sweep point gets the slots the queue picked (Section 8). A `--workers-per-gpu` below 1 is refused on that path (`parallel.py:536-537`).
- Each worker gets `CUDA_VISIBLE_DEVICES=<one physical id>` (`parallel.py:568-569`), so the decoding YAML must say `device_idx: 0` (docstring `parallel.py:6-9`). `physical_ids` (`parallel.py:116-132`) maps the torch index `k` to the k-th entry of the launcher's own `CUDA_VISIBLE_DEVICES`, stopping at the first empty entry "as in CUDA" (`parallel.py:120`), and exits on an out-of-range index.
- `launch.yaml` records the targets and the ordered list of `{name, device}` per worker (`launch_record`, `parallel.py:579-581`; written at `parallel.py:697-698`), and `merged_result.yaml` repeats the device in each `per worker` row (`parallel.py:814-840`), keyed by worker name (`parallel.py:873`).
- `spawn_workers` (`parallel.py:650-667`) uses `Popen(..., start_new_session=True)` (`parallel.py:660`) and appends stdout and stderr to `<wdir>/syndrilla.log` (`parallel.py:654`). The new session means a Ctrl-C in the terminal reaches only the launcher, which catches it (`parallel.py:933-937`), stops every worker and exits 1 without a merge.
- A CPU decoding YAML collapses to one worker `w0` on device `cpu`, whatever device list was given (`parallel.py:530-534`); `run` prints the note that `--gpus` and `--workers-per-gpu` are ignored. For that worker the launcher sets no `CUDA_VISIBLE_DEVICES` (`parallel.py:568`); an inherited one passes through, because the probe and the spawn build the child environment as `dict(os.environ, **env)` (`parallel.py:619`, `657`). `decoding_device` (`parallel.py:443-456`) reads the device type from the `-d` YAML in the passthrough flags.
- Argument hygiene: the parser sets `allow_abbrev=False` (`parallel.py:341`) and registers `-ckpt`, `-t`, `-tr`, `-tckpt` as hidden flags (`parallel.py:93-98`, `330-333`). The parser then catches these flags and refuses them instead of passing them through (`parallel.py:416-418`). Every other unknown flag goes to each worker unchanged (`parse_known_args`, `parallel.py:407`).

## 2. Target splitting and the pooled stop

**Problem.** The user gives one target, `-te` (logical errors) or `-tb` (batches), or both. Workers run at different speeds and cannot see each other. The run must stop close to the target without a shared counter.

**Importance.** Over-shooting wastes GPU time; under-shooting breaks the statistics the user asked for. A shared counter would need inter-process communication and would die with the launcher.

**Innovation.** Two regimes. With one target, the launcher splits the target into integer shares that differ by at most one and sum to the target. Each worker stops on its own share, so no coordination is needed. With both targets, every worker gets the full `-tb` as a safety net. The launcher then implements the `-te` stop itself: it sums the saved YAMLs on each poll and sends SIGTERM when either pooled count is reached, whichever comes first.

**Implementation.**
- `split_target` (`parallel.py:110-113`): `base, rem = divmod(total, n)`, then `[base + (k < rem) for k in range(n)]`, so the lowest worker indices carry the remainder. A target below the worker count is refused (`worker_shares`, `parallel.py:465-466`).
- The worker flag is `-tb` when `-tb` is given, else `-te` (`args.worker_target`, `parallel.py:427-430`); a worker never receives both. `args.pooled` is true only when both are given (`parallel.py:426`); then `shares = [target] * count` with `-tb` as the target (`parallel.py:463-464`).
- Lone `-tb` ends exactly at the target: `main.py` counts primary batches only (`main.py:483`) and stops at `num_batches < max_batches` (`main.py:421-423`, `443`). Lone `-te` ends at or above: the loop condition is `num_err <= error_budget` (`main.py:443`), so a worker generates one more batch when it has exactly its share.
- `pooled_now` (`parallel.py:670-688`) re-reads each worker's `result_phy_err_*.yaml` and sums `shots`, `fails`, `batches` from each worker's last good read. A YAML caught mid-write fails to parse, and the next poll reads it again (`parallel.py:675-681`). The launcher does not detect a cut that still parses.
- `step` (`parallel.py:721-774`) checks `fails >= target_error` first, then `batches >= target_batch` (`parallel.py:740-743`), records the rule and the pooled values seen (`parallel.py:763-765`), and calls `terminate()` on every live worker (`parallel.py:771-773`). If every worker exits on its own `-tb` before a pooled rule fires, `finish` records `worker targets` (`parallel.py:796`). An exit code of `-SIGTERM` after a pooled stop is not a failure (`parallel.py:731-734`).
- Consequence not stated in the docs: with both targets, the stop point depends on wall-clock poll timing, so the pooled counts are not reproducible across launches even with `--seed`. With one target, each worker's stop depends only on its own stream, so they are.

## 3. The SIGTERM contract and the overrun bound

**Problem.** The launcher must stop a worker from outside, without losing the batch in flight, the deferred queue, or the metrics since the last save.

**Importance.** A kill at an arbitrary point loses shots since the last save and can leave deferred samples undecoded, which biases the logical error rate (deferred samples are the hard ones).

**Innovation.** SIGTERM only sets a flag. The worker checks the flag at the loop head, so the current batch always completes. The worker then treats the budget as spent, which triggers the normal end-of-run path. That path drains the deferred queue in uncapped batches (the last one can be partial, `utils.py:820-826`), then saves with `done=1`. Stopping is the same code path as finishing.

**Implementation.**
- Handler: `signal.signal(signal.SIGTERM, lambda *_: stop.update(requested=True))` (`main.py:432`), installed only in the main thread (`main.py:431`); the comment at `main.py:427-429` explains that logging inside a handler can deadlock. The previous handler is restored on exit (`main.py:168-177`).
- `budget_left()` (`main.py:434-443`) returns False once requested and logs once "SIGTERM received at batch {n}; stopping and saving the final result."
- The loop is `while budget_left() or (cap_on and queue.nonempty)` (`main.py:450`); the flag is read only there and in `use_extra` (`main.py:464`), never inside the batch body (`main.py:451-618`). After the budget ends, `use_extra` forces one deferred batch per pass (`main.py:464-469`) until the queue is empty, then `save_metric(..., done=1)` runs (`main.py:627-645`).
- The overrun bound (docstring `parallel.py:27-30`) is the sum of four terms, each visible in code:
  1. Save interval: counts come from saved YAMLs; a worker saves at `num_batches % save_interval == 0` (`main.py:591-592`), default 100, minimum 100 (`main.py:142-147`, `163-164`; `parallel.py:419-420`). The save also waits for an empty deferred queue (`main.py:597`), so a YAML can be older than the interval when the cap has parked rows.
  2. Poll interval: `next poll = start + poll_interval` (`parallel.py:712`, advanced at `736`), default 60 s (`parallel.py:307-312`).
  3. The batch in flight (loop-head check only, `main.py:450`).
  4. The deferred-queue drain (`main.py:450`, `464-469`), which adds shots and fails (`main.py:561`) but no batches (`main.py:483`).
- The code expresses no upper bound beyond these terms; the pooled totals end at or above the target.

## 4. Per-worker resume with layout refusals

**Problem.** A stopped or killed launch must continue from where each worker was, with the same statistics, and must not silently merge results from a different layout.

**Importance.** Merging a resumed worker with a different share, seed or device, or a single-run YAML with worker YAMLs, gives a pooled result whose provenance is wrong.

**Innovation.** Resume is per worker and needs no launcher-side state beyond `launch.yaml`, which carries the ordered worker list with a physical device each. The launcher restarts each worker directory that holds a result YAML with `-ckpt` pointing at that YAML, on the device the record names. It checks the layout before any worker starts, and it refuses rather than repairs: a different worker count, order or device set is a different layout, and so is the old `gpu<g>_w<j>` tree.

**Implementation.**
- `plan_workers` passes `-ckpt=<yaml>` for each worker dir that holds a result YAML (`parallel.py:551`, `565-566`); logs are appended (`parallel.py:654`).
- Refusals, all in `preflight_workers` (`parallel.py:470-524`) before launch. An old-layout run dir, any `gpu*_w*` or `cpu_w*` directory, exits with "holds an old worker layout (gpuG_wJ/cpu_w0); flat-worker launches cannot use it. Use a new -r directory." (`parallel.py:477-481`); a `launch.yaml` without a `workers` list exits as "an old worker layout without recorded devices" (`parallel.py:500-501`). The launcher refuses a run dir that holds a single-run YAML but no `launch.yaml` and no worker dir, and prints the `syndrilla -ckpt` command that resumes it (`parallel.py:485-491`). It refuses `w<i>` dirs that differ from the planned set (`parallel.py:482-483`, `492-495`), recorded workers whose count or `w<i>` names differ, or whose device is not a non-empty string (`parallel.py:502-508`), `launch.yaml` targets that differ from this launch (`parallel.py:509-512`), worker dirs with no `launch.yaml` at all (`parallel.py:513-514`), and a worker YAML whose `decoder_full[target_key]` differs from this launch's share (`parallel.py:515-523`). In `sweep`, a point folder that already holds `merged_result.yaml` is counted done and never preflighted, so a finished old-layout point keeps its result; only an unfinished one is refused (Section 8). `plan_workers` then requires the recorded list to equal the planned list including physical devices (`parallel.py:543-545`), for a `run` and for a sweep point alike, so a `run` resume needs the same `--gpus` and `--workers-per-gpu`, and a sweep point resumes only on its recorded devices (Section 8). `launch.yaml` records neither `--seed` nor `--save-interval`, so only the worker's own warning detects a seed mismatch (`main.py:266-270`).
- `start_launch` writes `launch.yaml` (`parallel.py:697-698`) and deletes any stale `merged_result.yaml` and pooled `result_phy_err_*.yaml` (`parallel.py:699-704`), so a failed launch leaves no pooled file behind.
- Worker restore (`metric.py:810-839`, `842-937`) reads `batch count`, `target error reached`, and per decoder `sample count` and `total time`. It multiplies the saved averages back into accumulators (`metric.py:888-896`, `908-935`). It rebuilds the iteration histogram from `iteration count` (`metric.py:899`). A histogram that does not sum to the sample count is replaced by zeros with a warning (`metric.py:900-906`). `save_metric` writes `iteration count` as the raw histogram at every save (`metric.py:755-756`), which is what makes the rebuild possible. The percentile `iteration distribution` is written only at the final save; periodic saves hold the raw histogram in both fields (`metric.py:659-671`). `validate_checkpoint` (`metric.py:939-969`) requires equal batch size, targets, dtype, physical error rate and H file name.
- Not restored: the RNG state, which is reseeded (Section 6). Not restored: the rebatch cap's warm-up. The checkpoint has no cap field; the YAML carries only `rebatch_opt: {warmup batches, chosen pct}` (`metric.py:602-609`), so the cap re-warms on each resume. Not restored: the deferred queue, which is empty by construction at every save (Section 9).

## 5. The probe

**Problem.** A bad YAML, a decoder that silently falls back to CPU, or an out-of-memory at the chosen batch size would otherwise surface minutes later, once per worker, and after worker directories exist.

**Importance.** With N workers the same failure repeats N times and leaves N half-made directories; a CPU fallback would run for hours at the wrong speed.

**Innovation.** Decode one batch (`-tb=1`) with the real flags on the first worker's GPU in a scratch directory, before any worker directory exists, and inspect both the exit code and the worker log for the fallback warning. The probe also warms the torch extension cache once, so workers do not all compile the CUDA extension at the same time.

**Implementation.**
- `probe` (`parallel.py:598-647`): records which of `run_dir` and its parents it creates (`parallel.py:604-609`), makes `tempfile.mkdtemp(prefix="probe_", dir=run_dir)` (`parallel.py:610`), runs `probe_cmd` = `python -m syndrilla.main -r=<probe_dir> <passthrough> -tb=1` (`parallel.py:589-595`) with the first worker's environment (`parallel.py:927`), output to `probe.log` (`parallel.py:614-620`).
- Checks: a non-zero exit prints the last 5 lines of `main-*.log` and 12 of `probe.log` and exits (`parallel.py:623-630`). A grep for `"unavailable input device"` in `main-*.log` (`parallel.py:631-639`) catches the CPU fallback when the YAML says cuda. There is no explicit memory or import check: memory is caught only through the exit code, and the docstring states the probe does not catch pressure from several workers on one GPU (`parallel.py:42-43`).
- Cleanup (`parallel.py:641-646`): the scratch dir is removed, unless the probe failed and `run_dir` pre-existed, in which case `probe.log` is kept and its path printed; directories the probe created are removed again on failure. In `sweep` the probe runs inline per point and blocks the poll loop of running points for its duration (`sweep.py:268-269`).

## 6. Seeding per worker and across a resume

**Problem.** Workers must draw different shots, the same command must draw the same shots again, and a resume must not replay the shots already counted.

**Importance.** Two workers with the same seed double-count the same shots; a resume that reseeds with the base seed replays the first batches and biases the pool.

**Innovation.** The launcher gives worker i the integer seed `base + i` over the flat list and nothing else. On resume, the worker mixes that base seed with the checkpoint's batch count through a `splitmix64` hash. The launcher therefore never tracks a mixed seed. The result YAML records the base seed, so an unseeded resume reuses it.

**Implementation.**
- Launcher: `seed = args.seed + i` over the flat worker index (`parallel.py:552`). The launcher passes `--seed=<seed>` only when `--seed` is given (`parallel.py:563-564`); an unseeded resume reads the seed back from the checkpoint's `decoder_full.seed` (`parallel.py:554-559`). In `sweep`, point i in sorted folder order gets base `b + i*w` with `w = --workers-per-point` (`sweep.py:184-185`), so worker j of point i gets `b + i*w + j`. Seeds therefore stay stable across resumes only while the set of point folders is unchanged.
- Worker fresh run: `torch.manual_seed(seed)` and `random.seed(seed)` (`main.py:273-276`). numpy is not seeded. Resume: the worker reads the checkpoint's `decoder_full.seed` (`main.py:258-272`). An explicit `--seed` that differs wins with a warning (`main.py:266-270`). The worker then sets `seed = resume_seed(base, batch_count)` (`main.py:272`). `resume_seed` (`main.py:42-52`) returns `base` at n == 0, else `splitmix64(splitmix64(base) + n) & (2**63 - 1)`. Its docstring notes that `(base, n)` and `(base + 1, n - 1)` differ, and that the mix changes the low 32 bits, "which is all torch's CPU generator keeps". An unseeded checkpoint resumes unseeded.
- The seed reaches the error model only through the global torch RNG. No module creates a private generator: `bsc.py:65`, `80`, `98-99` call `torch.rand` or `torch.rand_like`; `depol.py:43` calls `torch.rand_like`; `stim_circuit.py:228` calls `torch.randint` and `:246` and `:254` `torch.rand_like`; the phenomenological measurer calls `torch.bernoulli` (`syndrome/phenomenological/phenomenological.py:93`). `bp_lottery_parallel` draws replica seeds from the global RNG when `seeds` is absent, so a resumable run should set `seeds` (`docs/decoder.md:457`).
- Recorded as `decoder_full.seed` (`metric.py:785`; `main.py:615`, `644`), the base seed, not the mixed resume seed.
- What this guarantees, as far as the code states: distinct integer seeds per worker and reproducible per-worker streams given the same seed, flags and device. The code does not claim that consecutive seeds give non-overlapping streams, and nothing addresses whether the CUDA stream is identical across GPU models. A different worker count changes both the shares and the seed map, so the merged result changes; a resume with a different layout is refused (Section 4).

## 7. The merge and the Wilson interval

**Problem.** N worker YAMLs, possibly resumed, possibly one missing, must become one result in the single-run schema plus a provenance record, with an uncertainty that does not collapse at zero failures.

**Importance.** The normal approximation gives a zero-width interval at zero failures and a negative lower bound at small counts, exactly the regime of low-p decoding sweeps.

**Innovation.** One pass writes two outputs. `merged_result.yaml` is the provenance record: one row per worker, the stop rule that fired with the pooled values read at that moment, and the resumed and missing workers. The pooled `result_phy_err_<rate>.yaml` keeps the single-run layout, so downstream tools read it unchanged. The merge sums the counts and recomputes the rates from the sums. It sums the histograms element-wise, so the pooled percentiles are exact rather than averaged. The interval is Wilson at z for 95 percent.

**Implementation.**
- `merge` (`parallel.py:799-896`) excludes and lists workers with no YAML (`parallel.py:805-806`, `857`). It refuses workers with differing physical error rates (`parallel.py:843-847`). It sums `batches`, `shots`, `fails` and the iteration sums (`parallel.py:848-851`, `862`). It recomputes `logical error rate = fails / shots` (`parallel.py:852`, `865`), the Wilson interval (`parallel.py:853`, `866`), and `average iteration` (`parallel.py:867`). It sums the per-worker rates into `shots per decode second` (`parallel.py:868-870`) and divides new shots by launch wall for `shots per wall second (this launch)` (`parallel.py:871`). In the pooled file, the launcher's targets overwrite `decoder_full["target error"/"target batch"]` (`parallel.py:879-880`) under the `POOLED_NOTE` comment (`parallel.py:100-107`).
- `pool_results` (`parallel.py:189-240`) handles each `decoder_i` entry. It sums the sample counts. It sums `iteration count` element-wise with `zip` (`parallel.py:206`); if the histograms differ in length, `zip` silently truncates to the shortest, and nothing guards against that. It rebuilds `iteration distribution` with `percentiles` (`parallel.py:174-186`), which mirrors `metric.py:662-669`. It drops `rebatch_opt` (`parallel.py:217-218`) and weights the remaining scalars by sample count (`parallel.py:223-226`).
- `wilson(fails, shots, z=1.959963984540054)` (`parallel.py:135-143`) computes `p = fails/shots`, `den = 1 + z^2/n`, `center = (p + z^2/(2n))/den`, `half = z*sqrt(p(1-p)/n + z^2/(4n^2))/den`, clipped to [0, 1]; it returns `[0, 1]` at zero shots. `summary` (`parallel.py:159-171`) feeds it the last decoder's `sample count` and `decoder_full["target error reached"]`, that is, the logical errors of the last decoder in the chain (`main.py:561`). The interval appears in `merged_result.yaml` (per worker at `parallel.py:825-827`, pooled at `866`), in the progress line (`parallel.py:755-761`), the final print (`parallel.py:888-895`), and the sweep CSV (`sweep.py:47-48`, `147-149`, `322`). The pooled `result_phy_err_<rate>.yaml` does not carry it; its `decoder_full` block holds only the summed counts and times (`parallel.py:229-239`).

## 8. Sweep mode as a queue over GPU slots

**Problem.** A sweep over code, p, d and dtype is many independent launches of unequal length. Running them one after another leaves GPUs idle; running them all at once oversubscribes memory.

**Importance.** A d=27 point can run for hours while d=3 points finish in seconds; a static assignment of points to GPUs serializes on the slowest.

**Innovation.** Points form a queue, and GPUs form slots (`--workers-per-gpu` per GPU). A point starts when `--workers-per-point` (w) slots are free anywhere, and it takes them spread over the emptiest GPUs first, doubling up on one GPU only when nothing emptier is free. Because a worker is just a device string (Section 1), a point can have two workers on one GPU and one on another without a special case. The sweep plans every point, with all refusals, before the first one starts, so a bad folder cannot stop a sweep halfway. Each point is a complete `run` (probe, `launch.yaml`, worker dirs, pooled stop, merge, resume), so a per-point failure stays contained, and a resumed point is pinned to the devices its `launch.yaml` recorded.

**Implementation.**
- `sweep-gen`: `generate` (`sweep.py:88-121`) takes the product over `decoder, code, check_type, probability, distance, dtype` (`sweep.py:99-103`), refuses more than one decoder (`sweep.py:94-98`), and `write_point` (`sweep.py:54-85`) sets `max_iter` from the distance (`sweep.py:61-64`: surface `d*2*(d-1)+1`, else `d*2*d`). `zoo/script/generate_sweeping_configs.py` is a thin wrapper over `syndrilla.sweep.generate`.
- `run_sweep` (`sweep.py:162-334`) refuses a `--workers-per-point` or `--workers-per-gpu` below 1 (`sweep.py:168-170`) and a w above the total slot count, GPUs times `--workers-per-gpu`, when any point needs a GPU (`sweep.py:207-208`). The points are the sorted folders that hold a `*.decoding.yaml` or a `merged_result.yaml` (`sweep.py:171-175`). The preflight loop (`sweep.py:180-201`) first counts a folder with `merged_result.yaml` as done and rebuilds its CSV row from that file with status `done`, skipping every layout check (`sweep.py:188-194`), so a point finished under the old `gpu<g>_w<j>` layout keeps its result; it then sets the base seed of each other point, runs `preflight_workers` on it, which refuses an unfinished old-layout folder (Section 4) and stops the whole sweep before any point starts, and refuses a CPU/GPU mismatch between its `launch.yaml` and its decoding YAML (`sweep.py:198-199`). A CPU point is preflighted with width 1 (`sweep.py:196-197`). A started point is pinned to the GPU slots of its recorded devices (`sweep.py:209-221`); a recorded device outside `--gpus` or needing more slots than `--workers-per-gpu` gives is refused (`sweep.py:215-220`).
- Slot pick: `free_slots` (`sweep.py:156-159`) lists every free slot as `(gpu, rank)` and sorts by the load the GPU would have after taking it, ties to the lower GPU index, so every GPU's next slot comes before any GPU's second slot. A pinned point waits until each of its GPUs has room for its count (`sweep.py:249-251`); any other GPU point takes `free[:w]` (`sweep.py:252-255`). CPU points share one cpu slot of capacity 1, a flag beside the GPU loads (`sweep.py:239`): the head point starts when the slot is free (`sweep.py:246-248`, `259-263`), and the slot is released when the point finishes or fails to start (`sweep.py:276-277`, `285-286`). The pick looks at the head of the queue only, so a head point that waits, cpu or pinned, holds the points behind it. The chosen slots become physical ids and go to `plan_workers(..., devices=assigned)` (`sweep.py:266`), with a "starting on devices" line.
- Queue loop (`sweep.py:241-309`): the point probes inline (`sweep.py:267-269`), then `start_launch` (`sweep.py:270`). A `SystemExit` from probe or start marks the point failed and frees its slots (`sweep.py:272-280`). Running points advance with `par.step` (`sweep.py:281-283`), then `par.finish` and `par.merge` (`sweep.py:284-300`). `--dry-run` prints each worker with its physical device and command, picked against an empty load, so every point shows the first-slot pick rather than the assignment a run would make (`sweep.py:226-236`).
- Failure policy: default continue and exit 1 at the end listing the failed points (`sweep.py:330-334`); `--fail-fast` sends SIGTERM to running points and clears the queue (`sweep.py:301-308`). The `finally` block (`sweep.py:313-329`) stops every unfinished point, rebuilds its row from `pooled_now` with a Wilson interval and status `stopped`, and always writes `sweep_results.csv` (fields `sweep.py:37-51`).

## 9. Interaction with the `rebatch_opt` deferred queue

**Problem.** With the iteration cap on, the first decoder parks unconverged samples in a deferred queue and decodes them later in batches of up to `batch_size` (`utils.py:820-826`). A stop, a save, or a batch count must not lose, double count, or carry over these samples.

**Importance.** Deferred samples are the hardest shots; dropping them lowers the measured logical error rate. Counting them twice raises it. A checkpoint with pending rows could not be resumed without replaying them.

**Innovation.** The worker, not the launcher, enforces three invariants. A save waits for an empty queue. The end of budget, SIGTERM included, drains the queue before the final save. Drain passes add shots and errors but never batches. The launcher therefore needs no knowledge of the cap beyond the one overrun term in Section 3.

**Implementation.**
- Deferral: only the first decoder's cap defers (`main.py:367-377`). `bp_norm_min_sum` sets the `defer` mask over the unconverged rows of a batch the cap stopped early (`bp_norm_min_sum.py:447`, `497-504`; CUDA `bp_norm_min_sum_cuda.py:645-669`). `main.py` removes those rows from the batch metrics with `bt.keep_samples(cap_keep)` (`main.py:537-545`) and parks `err, llr0, synd, obs` in `ExtraQueue.defer` (`utils.py:798-812`). Re-decode runs uncapped (`cap_bypass`, `main.py:466`; `utils.py:771-777`).
- Drain triggers: `main.py:463` calls `queue.should_flush` (`utils.py:814`), which wraps `should_flush_extra_queue` (`utils.py:734-767`). With `-te`, the queue flushes when it is predicted to hold the remaining errors. With `-tb`, which is what pooled-mode workers receive, it flushes when it holds a full batch (`utils.py:758-759`). `save_due` or `not budget_left()` also force a drain (`main.py:464`).
- Save invariant: `if save_due and not (cap_on and queue.nonempty)` (`main.py:597`, comment `445-447`), so a checkpoint never carries deferred rows and a resume cannot replay them.
- Counting: `main.py` removes deferred rows from the primary batch's metrics before `report_metric` (`main.py:545`) and counts them once on re-decode (`main.py:561`, `578-589`). A drain pass does not increment `num_batches` (`main.py:483`).
- Loss case: a hard kill (SIGKILL, crash, out-of-memory) loses everything since the last save, deferred rows included. The resume restarts from the last YAML with a new mixed seed, so the worker counts nothing twice and redraws the lost shots. This is inferred from `main.py:591-597` and `258-272`; the docs do not state it.
- Stop overrun: in `-tb` mode the queue flushes once it holds `batch_size` rows (`utils.py:759`), and the check runs before the current batch defers its rows (`main.py:463-464`, `543`). At SIGTERM the queue therefore holds under `batch_size` rows plus one batch's deferrals, under about two batches. The drain decodes them all before the final save. This drain is the fourth term of the overrun bound.
